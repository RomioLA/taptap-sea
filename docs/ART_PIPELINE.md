# 《渔夫漂流记》2.5D 美术生产与接入基线

> **Status: ACTIVE BASELINE**
>
> 生效日期：2026-10-05。
> 适用范围：主航海场景、美术资产生成、图片接入、风格统一、昼夜表现、船/岛/漂浮物/海面信号等视觉工作。
> 未经用户明确确认，不得自行改变本文件规定的技术路线。

## 0. 文档地位与使用方式

本文件是当前美术生产与接入的项目级规则，不是某一次任务的临时建议。

执行任何主场景美术、Maker 资源生成、图片接入或风格调整任务前，必须先阅读本文件；需要改代码时还必须读取当前真实源码，不得只凭本文中的实现摘要直接修改。

本文件区分两类内容：

- **冻结规则**：明确规定后续工作应遵守的方向，除非用户重新拍板，否则不得自行更改。
- **当前实现事实**：用于说明现有接入点和已知缺口；源码可能继续演进，因此实施前必须重新核对真实代码。

如果本文与当前源码出现差异：先报告差异，判断是“规则尚未落实”还是“源码已演进”；不得为了让源码看起来符合文档而擅自重写实现，也不得默默把规则改成当前代码的样子。

## 1. 冻结技术路线

当前主航海画面采用：

**UrhoX + Lua + NanoVG + 世界米制坐标 + 自实现斜视投影的 2D/2.5D 渲染。**

必须保持以下边界：

1. 不因为美术接入改成传统 3D Scene / Model / Material 资产链。
2. 不为了接 PNG 把已经存在的斜视投影整体改回纯屏幕空间俯视 2D。
3. 当前美术主线不依赖 Spine；人物演出若以后需要，另开任务评估，不反向改变主航海资产管线。
4. 美术任务默认不得修改船移动、鱼 AI、碰撞、刷新、交互、昼夜规则、存档或其他核心玩法逻辑。
5. 视觉资产替换应复用当前世界坐标、投影、可见性、排序与回退机制，而不是复制一套平行世界或屏幕坐标系统。

当前真实链路需要按源码重新核对，但截至本基线建立时，主路径为：

`Main.lua → Integration.Scene → Ocean.FusedScene → Ocean.Bootstrap → Ocean.SeaDraw / Ocean.SeaViewArt`

`Ocean.Bootstrap` 创建 NanoVG context，并在 `NanoVGRender` 中 `nvgBeginFrame / nvgEndFrame`；`Ocean.Projection` 负责世界平面到屏幕的斜视投影。该事实意味着本项目不是传统 3D 模型渲染管线。

## 2. 现有图片接入链是唯一默认主线

截至 2026-10-05，项目已经存在正式图片适配层：

- `scripts/Ocean/ImageArt.lua`：NanoVG 图片加载、释放、平面分片投影、Sprite 尺寸补偿、海面纸纹和接触波纹。
- `scripts/Ocean/Projection.lua`：当前世界斜视投影、地平线曲率、高度与远端遮挡。
- `scripts/GeneratedData/OceanImageCatalog.lua`：运行时只读图片规格目录，**自动生成，禁止手工编辑**。
- `tests/prepare_ocean_ready_art.py`：当前新增航海图片素材的整理、清理、规格生成和一致性检查入口。
- `scripts/Tests/OceanImageCatalogTests.lua`：目录、加载失败回退、透明留边尺寸补偿、释放等契约测试。

因此后续默认规则是：

1. **不得另建平行的 `art_spec.lua`、第二套图片目录、第二套 ImageArt 或另一套世界投影。**
2. 新增运行时图片规格确有需要时，应扩展现有素材清单/生成脚本及其生成结果，而不是直接手改 `GeneratedData/OceanImageCatalog.lua`。
3. 图片加载失败必须保留现有矢量 fallback；不得为了“正式换美术”直接删除仍承担回退和几何职责的矢量路径。
4. 图片接入不得成为新的玩法状态来源；`ImageArt` 只负责表现和资源句柄，不持有实体、不更新世界。
5. 修改 `Projection` 属于高风险渲染架构修改，不能仅因为某张 PNG 视角不合适就调整投影去迁就素材。

## 3. 不使用固定“作画俯角 θ”匹配游戏投影

这是硬规则。

当前 `Ocean.Projection` 不是一个可以用单一“俯视角 θ + 固定纵向压缩比”完整描述的简单斜投影。其屏幕尺度随世界深度变化，远端还包含地平线曲率、遮挡与高度投影。

因此：

- 不从 `Projection` 反推一个固定 θ 作为所有 Maker 提示词的作画角度。
- 不要求平面 PNG 预先画成游戏最终斜视角。
- 不用“先把图画斜，再由 `ImageArt.Plane` 投影”的双重透视方案。

对于贴在海面/世界平面的资产，默认生成基准应为：

**正俯视 / orthographic top-down / 无预烘焙斜视透视。**

`ImageArt.Plane` 会把图片切成世界平面网格并通过现有 `Projection` 投到屏幕。素材负责“长什么样”，游戏负责“在当前相机和深度下怎么看”。

只有明确属于竖直 Billboard / 立面表现的资产，才另开任务定义其朝向、锚点与投影策略；不得把这种规则反推给所有平面素材。

## 4. 资产生产规则

### 4.1 通用输出要求

Maker / Maker MCP 是当前默认美术生成入口。生成或整理后的正式候选资产应进入项目 `assets/` 资源流程，并继续由现有目录/生成脚本管理；临时源图、候选图和正式运行时图的路径由具体任务明确，不得覆盖不相关现有素材。

平面世界资产默认遵守：

- RGBA PNG，透明背景。
- 正俯视 / orthographic top-down；不要预烘焙当前游戏斜视透视。
- 不把地面投影、海面倒影、尾流、水花等环境效果烘进主体 PNG；这类效果由程序/独立效果资产承担。
- 固有色清晰，方向光保持很弱，避免强烈单向高光和大块固定阴影导致昼夜染色失真。
- 保留足够透明留边，避免旋转/投影时裁切；同时记录实际可见主体 bounds，绘制尺寸按可见主体而不是整张画布估算。
- 有明确朝向的资产必须声明源图朝向。当前世界 heading 约定应读取当前代码/素材清单，不凭记忆推断。

### 4.2 锚点不是“一律 bottom-center”

资产先按表现类型分类：

**Planar（贴世界平面）**：船、木桶、漂浮物、岛面、礁石、波纹等。默认以世界对象中心与图片可见主体中心稳定对应；现有 `ImageArt.Plane` / `Sprite` 及当前 catalog 以中心基准为主。

**Upright（竖直/立面）**：未来可能出现的树、灯塔、人物、竖立标牌等。此类资产才可能需要 bottom-center/脚点锚定，并且必须另行确认 Billboard、朝向、遮挡和高度规则。

不得因为某类 Upright 资产需要脚点，就把所有海面平面资产统一改成 bottom-center。

注意：catalog 中存在 `anchorX/anchorY` 字段，不等于所有现有绘制路径都已经消费该字段。若任务要求新增非中心锚点，必须先核对当前 `ImageArt` 实现并补测试，不得只改数据宣称生效。

### 4.3 世界尺寸与像素尺寸

逻辑尺寸以世界米制尺寸为准；PNG 像素分辨率是采样质量，不得反过来成为碰撞/交互尺寸来源。

生成分辨率应根据该资产在最近合法可见距离下的最大屏幕占用评估，并留清晰度余量。可以把“最大预计屏幕像素 × 约 1.5–2”作为首轮经验值，但不是硬编码公式；最终必须用运行时最近距离实测确认“不过糊也不过度浪费”。

碰撞半径、交互距离、鱼行为范围等继续来自世界/玩法数据，禁止从 PNG alpha、画布大小或 content bounds 自动推导玩法判定。

## 5. 风格基线与可读性

当前主风格：**清爽水彩绘本 / 海边童话**。

生产目标不是把每一帧做成高密度概念插画，而是让完整游戏画面统一、安静且能读规则。

必须保持：

- 海面大区域视觉安静，水彩纹理是低频材质感，不用密集杂斑抢信息。
- 天空、岛屿、船、漂浮物和功能信号属于同一套水彩绘本语言。
- 功能信号（海鸟聚集、水花、波纹、气泡、鱼跃等）必须比纯装饰元素更容易识别。
- 参考风格锚图用于统一笔触、色彩、复杂度和留白，但不得要求 Maker 把整张参考画面构图复制到单个资产。
- 批量出图时使用稳定的风格模板；不得每个物件重新自由发挥提示词导致风格漂移。

“克制/突出”目前不以某个单一颜色数值替代视觉验收。若后续需要量化，应以实际场景中的识别率、对比和误认测试补充，而不是先凭空制定不受当前渲染支持的阈值。

## 6. 海面与环境材质

连续海域不使用一张巨大 AI 背景图替代世界。

正式方向是：

**程序海面底色/投影/动态波纹/地平线 + 少量可平铺低 Alpha 水彩材质层。**

当前 `ImageArt.WaterPaper` 已经提供纸纹材质层入口，现有动态波纹仍由程序维护。后续海面素材应优先生成：

- 无缝水彩纸纹；
- 低频水面笔触；
- 柔和噪声/晕染；
- 可选局部反光材质。

约束：

- 强制做无缝检查，避免相机移动时暴露接缝。
- 默认控制在少量材质层；新增层必须看实际性能，不因“更丰富”无上限叠加。
- 功能波纹、水花、尾流不烘进基础水面纹理。
- 海面材质不能压过海鸟、水花、鱼跃等玩法信号。

## 7. 昼夜处理基线

当前决策：**一套主体 PNG + 程序化昼夜处理**，不默认为每个资产制作昼/夜双套图。

资产侧规则：

- 主体 PNG 采用固有色 + 弱方向光。
- 不带大块固定投影、强高光或夜间专用发光。
- 真正需要发光的玩法对象必须另行定义发光层，不能把所有亮部都烘成不可控自发光。

当前实现存在一个明确待落实点：截至基线建立时，`SeaDraw.Scene` 的夜间覆盖在部分世界对象之前绘制，因此后绘制的 PNG 世界对象不会自动接受同一夜间压暗。后续昼夜美术任务必须先核对真实顺序，并保证：

1. 世界环境和普通世界资产接受一致的昼夜色调变化；
2. UI 不被世界夜色罩整体压暗；
3. 功能信号可以根据可读性选择较弱的夜间压暗，但不得无依据全部保持白天亮度；
4. 昼夜处理只改表现，不改玩法时钟或世界状态。

具体实现可以是世界层统一 overlay、图片 tint 或分层组合，但必须复用现有时钟与 NanoVG 能力，并通过实际画面验收后再固定，不在本文强制某一个 API 方案。

## 8. 船的专项规则

船是主视觉焦点，但不是改成 3D 的理由。

推进顺序固定为：

1. 先生成 **一张真正正俯视、无预烘焙透视** 的临时水彩船，用于尽早校准整体风格。
2. 复用当前 `ImageArt.Plane` 的连续 heading、heave、roll 和世界投影能力测试 360° 旋转。
3. 只有实际运行出现明确视角违和，才升级到多方向素材；不预设一定需要 8 方向。
4. 如果转多方向，方向数和切换策略另开小任务确认；不得直接扩成 16 方向或更多。

单图失败的判据包括但不限于：

- 斜向旋转时出现明显“看到不该看到的船底”；
- 船头/船尾透视方向与世界斜视关系反转；
- 甲板、船舷、帆的空间关系随旋转明显不成立；
- 旋转后的固定光影成为比几何更明显的违和来源。

船速等级目前是玩法速度等级，不自动等于三套船外观。除非策划明确要求升级后换船型，否则不得据此推导 `3 × 8` 等额外资产量。

尾流、接触水花和海面波纹不得画死在船 PNG 中，继续由程序/独立效果层随运动产生。

## 9. 深度排序、遮挡与世界逻辑

当前 `SeaDraw` 已经按世界 Y 做稳定 painter ordering，用于让较远的船/漂浮物/信号位于较近岛屿之后。同 Y 保留稳定顺序。

因此：

- 图片接入优先验证现有排序，不先另建新的“脚点 Y + layer”系统。
- 如果某类资产发生穿帮，先确认是世界 Y、实体半径、高度、图片透明边还是绘制顺序问题，再做最小修复。
- 透明 PNG 的可见形状不能改变实体的世界碰撞、交互范围或逻辑身份。
- 竖直资产若以后需要高度参与遮挡，应通过明确的 altitude/几何规则接入，不用屏幕像素高度猜世界高度。

## 10. Maker 生产与风格漂移控制

默认工作流：

**TapTap Maker / Maker MCP 生成 → 规格整理/清理 → 进入现有图片目录生成链 → Codex 接入/检查 → 本地运行 → 视觉验收 → 仅重做目标资产。**

每批生成前应固定：

- 风格锚图/参考；
- 通用风格提示词；
- 资产类型（Planar/Upright/Effect/UI）；
- 透明背景、视角、光照、是否允许自带阴影；
- 目标世界尺寸和用途；
- 是否属于功能信号。

不允许因为某一张结果不好就同时改变风格、视角、光照、尺寸和构图要求；优先做局部修正，以便定位 Maker 的实际能力边界。

当连续 2 批同类出图中，与风格锚图并排验收的不通过率超过 30%，或 Maker 无法稳定做到“只修改指定物件/区域而不破坏已确认部分”，才评估引入 ComfyUI 或其他外部图像工作流。引入外部工作流前需另行确认成本、依赖和资产交接方式。

## 11. 木桶最小闭环门禁

在批量替换美术前，先用一个低风险世界对象完成端到端 Spike。现有 `assets/generated/mcp_test_barrel.png` 可作为候选输入，但是否直接作为正式素材需按当前任务确认。

闭环至少验证：

1. 图片能被现有 NanoVG 图片路径加载，无资源错误。
2. 世界中心/视觉中心与原木桶位置稳定对应，可临时与矢量 fallback 对比。
3. 相机移动、船移动和视角变化时不漂移、不反向位移。
4. 远近缩放和斜视投影与周围世界一致。
5. PNG 只改表现；碰撞、5m 操作范围、木桶身份和教学逻辑继续由世界数据驱动。
6. 图片加载失败或显式切回时，矢量 fallback 仍可用；不删除回退路径。
7. 现有 painter ordering 下，船从不同方向经过木桶时没有明显前后穿帮。
8. 若木桶存在浮动/微摇表现，图片位移与旋转应跟随同一表现状态，不建立第二套运动。
9. 夜间不出现白天亮块、异常发黑、自发光错觉或与海面色调完全脱节。
10. 最近合法距离观察时清晰度足够，透明边无明显彩边/黑边。
11. 缩放、旋转、投影过程中视觉中心/既定锚点不跳动。
12. 性能至少做“正式单实例与矢量 fallback 无异常级回退”的实机场景比较；可额外做多实例压力测试，但正式游戏并不以必须同屏 20 个木桶作为产品门槛。

只有这个闭环成立，才批量推进岛屿、漂浮物、海鸟、水花/波纹/气泡、港口环境与 UI 图标等资产。

## 12. 资产推进优先级

当前建议顺序：

1. 木桶闭环（验证管线）。
2. 临时正俯视水彩船（尽早校准全局观感，不代表最终船定稿）。
3. 岛面 / 漂浮物 / 礁石等 Planar 静态资产。
4. 海鸟、水花、波纹、气泡、鱼跃等玩法信号。
5. 港口环境、UI、背包、商店、道具/图鉴图标。
6. 船的最终定稿与必要的方向资产升级。

人物演出、Spine、复杂角色动作当前不在此生产顺序内。

## 13. 文档和代码边界

本文件描述“规则”和“接入方向”，不复制完整实现细节。实际任务必须重新读取当前源码。

尤其注意：

- `scripts/GeneratedData/OceanImageCatalog.lua` 是自动生成运行时副本，不作为人工维护源。
- 资产生产状态（待生成/待验收/需重做等）不要塞进运行时代码目录，除非以后有明确工具契约；优先放任务清单或视觉生产文档。
- 不因为本文提到某个未来字段就预创建大而全的资源管理框架。
- 如果需要新增字段、生成脚本能力或 Upright 资产类型，先做小范围契约设计并补相应检查。
- 本文件不能替代 `docs/AI_RULES.md`、`docs/TEAM_FILE_BOUNDARIES.md` 和具体任务授权；涉及共享代码仍按既有协作边界执行。
