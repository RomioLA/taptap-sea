# 四人文件所有权与协作边界（第一版）

- 项目：2026 TapTap 聚光灯 21 天游戏创作挑战，4 人 AI GameJam。
- 基线日期：2026-10-01；任务：TASK-000。
- 原则：一份文件在同一时段只有一个明确修改者；先说明目标、文件、接口和验收，再让 AI 动手。

> 这是团队协作制度，不是自动权限锁。当前未安装文件锁、权限拦截、Git 保护或冲突检测系统，也未修改 TapTap 协作者权限。平台能编辑一个文件，不等于团队允许直接修改它。

## 1. 角色与决定权

| 成员 | 角色 | 默认负责区域 | 默认不得直接修改 |
|---|---|---|---|
| A | 主创 / 项目负责人 / AI 技术负责人 | `Main.lua`、`State.lua`，核心代码、接口接入、跨模块协调、最终确认 | 不擅自删除、覆盖其他成员工作；修改共享文件先交接 |
| B | 策划 / 游戏设计 | 分配给 B 的 `docs/` 策划文档、未来 `data/` 规则/数值数据 | `Main.lua`、`State.lua`、`Draw.lua`、`HUD.lua`；未分配字段的 `Config.lua` |
| C | 美术 / UI / 游戏视觉 | `assets/` 素材，以及分配给 C 的视觉规范文档 | `Main.lua`、`State.lua`、`Config.lua`；`Draw.lua`、`HUD.lua` 未获 A 明确分配时也不直接编辑 |
| D | 文案 / 世界观 / 事件内容 | 分配给 D 的 `docs/` 内容文档、未来 `data/` 故事正文 | `Main.lua`、`State.lua`、`Draw.lua`、`HUD.lua`；未分配字段的 `Config.lua` |

路径均相对项目根；上表的五个代码文件位于 `scripts/Main.lua` 或 `scripts/Ocean/`。

## 2. 文件保护等级

| 等级 | 文件 / 目录 | 默认所有权 | 操作边界 |
|---|---|---|---|
| 🔴 核心文件 | `scripts/Main.lua`、`scripts/Ocean/State.lua` | A | 其他成员先提出需求，A 确认后由 A 或 A 指定的 AI 实现；不得借 AI 绕过边界 |
| 🟡 公共表现文件 | `scripts/Ocean/Draw.lua`、`scripts/Ocean/HUD.lua` | A 负责程序逻辑和接入 | C 提视觉需求，B/D 提功能或内容需求；A 分配一个修改者，不多人同时编辑 |
| 🟢 配置 / 内容文件 | `scripts/Ocean/Config.lua`；未来 `data/` | Config 初期由 A 看护；B/D 按任务分配数据或字段 | 静态参数优先数据化，但“绿色”不是任意成员随意编辑的许可；仍须满足字段契约、单一修改者规则 |
| 🔵 美术资源 | `assets/` | C | 添加、整理和制作素材；替换已有文件先确认无人在使用且得到所有者授权，程序接入交给 A |

**核心文件只有 Main.lua 和 State.lua；其他文件虽非红色，仍可能需要 A 协调。** `.project/`、引擎版本、构建配置、入口设置等不是本制度授权的修改区域。变更设置必须另开明确任务；TASK-000 不修改它们。

## 3. A：主创 / AI 技术负责人

### 可以修改与负责确认

- `scripts/Main.lua`：游戏入口、输入、主流程与模块接线。
- `scripts/Ocean/State.lua`：状态数据、状态变化和核心运行接口。
- 经实际需求确认的新增核心系统、小模块及公共接口。
- 存档、事件系统、资源系统、航行系统、核心玩法逻辑的范围和最终确认。
- Draw/HUD 的程序接入、单一修改者分配和跨模块协调。

以上未来系统并非已经实现，也不是本任务的开发清单。

### AI 可以怎样帮助 A

只读分析、指定文件的小改动、明确 Bug 修复、必要接口接线和测试。AI 仍不得自行改引擎、设置、依赖、架构或任务范围。A 有最终确认责任，不代表 AI 获得无限权限。

## 4. B：策划 / 游戏设计

### 优先做数据，不直接改核心代码

初期使用被分配的 `docs/` 文档提出规则。未来 A 确认格式和读取接口后，可负责：

```text
data/                     # 建议，当前尚不存在
├── events/
├── items/
├── locations/
├── creatures/
└── lore/
```

策划参与事件、数值、航行消耗、探索结果、资源、生物、地点、涌现关系和游戏规则参数。

- 默认不能直接编辑 Main、State、Draw、HUD。
- Config 当前可被四个模块共享读取；初期只有 A 明确分配的已有配置字段可以修改，不能在其中增加规则函数、玩家状态或事件执行代码。
- 没有加载器或字段契约时，先提交提案，不猜测数据能直接运行。
- `data/events/` 与 D 共享：B 负责触发条件/数值/结果结构，D 负责正文；同一文件必须串行交接。

### 必须改代码才能实现时

停止代码编辑，提交：

```text
【策划需求】
关联任务：TASK-XXX
需要程序增加：

接口：
XXX

输入：
XXX

输出：
XXX

使用场景：
XXX

影响文件：
XXX（未知时写“待 A 确认”，不得自行扩大允许修改范围）
```

交 A 确认，由 A / 获授权的 AI 程序实现。B 的 AI 可以整理规则、提案、数据及验收用例，不能为了让策划方案“立即能玩”越权改核心代码。

## 5. C：美术 / UI / 游戏视觉

### 可以负责

在 `assets/` 添加、制作和整理素材；已有资源的替换须先确认所有权并按任务授权。内容包括船只、海洋元素、鱼群、海鸟、鲸鱼、岛屿、图标、UI 和特效。

推荐未来目录（本次不创建）：

```text
assets/
├── ship/
├── ocean/
├── creatures/
├── island/
├── environment/
├── ui/
└── vfx/
```

### 不能默认改代码

- Main、State、Config：除非 A 明确分配任务，否则不得修改。
- Draw/HUD：可以提出视觉方案；默认接入由 A 完成。若 A 分配视觉代码任务，必须列出允许文件与视觉范围，只能有一个修改者，不写核心规则或直接修改 State。
- 当前 Draw 使用程序化矢量图，没有图片接入。添加素材不等于素材会自动进入画面。

### 素材交接至少说明

文件路径、用途、尺寸/格式、透明背景要求、对应对象、是否替换旧资源、来源/使用许可，以及期望的显示比例或位置。C 提供素材和说明，A 确认路径并接入；不要让 C 的 AI 擅自修改入口、状态或资源系统。

AI 可以辅助视觉方案、素材规格、UI 资源和图标制作。需要外部生成服务时，遵守授权和费用确认，不自动外传团队未授权内容。

## 6. D：文案 / 世界观 / 事件内容

### 可以负责

被分配的 `docs/` 文档、未来内容数据：

```text
data/                     # 建议，当前尚不存在
├── events/
├── lore/
├── dialogue/
└── saga/
```

内容包括世界观、北欧萨迦、神灵、岛屿故事、NPC、航海日志、随机事件、涌现事件、发现文本和结局文本。

- 默认不能编辑 Main、State、Draw、HUD。
- Config 只可修改 A 明确分配的静态内容字段；当前不把正文大量塞入 Config。
- 事件正文与规则条件区分所有权：B 定规则/数值，D 写文本，A 定格式和接口。
- 内容需要选择分支、动态变量、日志记录等程序能力时：提出内容需求 → A 确认 → AI 在允许范围实现接口。

AI 可以辅助设定一致性、文本草稿、内容数据和测试案例，不可自行新增事件系统、存档或核心状态。

## 7. docs/ 和 data/ 不是无主共享区

B/D 均可参与这两个目录，但同一文件不能默认都拥有写权限。

| 文档 / 区域 | 初始负责人 | 其他成员的参与方式 |
|---|---|---|
| `PROJECT_STRUCTURE.md` | A | 发现差异先提出校正，不自行重写架构 |
| `TEAM_FILE_BOUNDARIES.md`、`AI_RULES.md` | A | 提规则修改建议，由 A 确认 |
| `TASK_BOARD.md` | A 协调维护 | 成员报告自己的任务状态；A 指定顺序更新，验收只由 A 确认 |
| `GAME_DIRECTION.md` | A 确认，B 主导设计提案 | C/D 提视觉与内容建议；编辑前先交接 |
| 未来策划 / 视觉 / 内容专属文档 | 对应 B / C / D | A 按任务分配具体文件 |
| 未来共享数据文件 | A 分配到文件或字段 | 同文件串行修改，不因“分字段”而同时保存整个文件 |

A 可确认新的专属文档和数据路径，但不提前创建大量空目录或占位架构。

## 8. Config 防膨胀规则

`Ocean/Config.lua` 只承担配置、参数、静态数据。

禁止同时塞入玩家状态、事件逻辑、UI 构建、移动更新、资源管理、存档和 AI。它是普通可变 Lua 表，当前没有冻结机制，所有修改均受所有权和范围约束。

实际需求使配置复杂后，A 再评估是否拆到 `data/`，并确认读取方式；本次不为未来提前重构，也不宣称已经支持数据驱动加载。

## 9. 跨模块修改规则

一个任务需要同时影响 Main、State、HUD 等多个模块时，先记录：

```text
【跨模块任务】
任务ID：TASK-XXX
影响：
- Main
- State
- HUD

需求与接口：
XXX

协调负责人：A
各文件修改者：由 A 分配
实施顺序与验收：由 A 确认
```

- 普通成员不能自行串改多个模块，AI 也不能为了“补齐功能”扩大范围。
- A 确认后，可指定 A / 一个 AI 按串行顺序修改多个允许文件；或者拆成小任务交接。规则不是禁止一切跨模块实现，而是禁止未经协调的实现。
- 新增文件也要登记，不可以通过新增模块间接改变未授权核心行为。
- 接口的参数、返回、状态读写和失败行为由 A 最终确认；B/D 提需求，C 提表现要求。

## 10. 什么时候必须立即停止并找 A

1. 必须修改允许范围之外的文件，尤其 Main 或 State。
2. 需要新增/改公共接口、状态字段、数据格式、ID、资源路径、入口、设置或依赖。
3. 出现跨模块需求，尚未标明影响文件和修改者。
4. 发现另一成员正在修改同一文件，文件内容已变化，或不知道当前版本是谁负责。
5. 需要删除、重命名、覆盖已有文件或其他成员工作。
6. 游戏无法启动、原有功能回归、缺资源或出现新的运行错误；只读记录问题，不扩大修改范围“顺便修”。
7. AI 建议更换引擎/技术栈、升级版本、大规模重构、引入大型依赖或提前执行未来任务。
8. 任务目标、验收、素材来源或费用授权不明确。

停止时保留当前改动和错误证据，写明任务 ID、发生了什么、影响文件和需要 A 决定的事项；未经确认不覆盖、不回滚别人的代码、不继续试改。

## 11. 一次任务的安全流程

A 分配任务与文件 → 当前修改者确认交接 → AI 只读核实 → 按允许范围小改 → 测试 → 提交报告 → 标记“待验收” → A 验收。

正式验收与稳定版确认由 A 执行，AI 不自行宣布项目完成。统一任务模板和提交报告见 [AI_RULES.md](AI_RULES.md)，看板见 [TASK_BOARD.md](TASK_BOARD.md)。
